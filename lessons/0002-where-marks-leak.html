Coupling tie-breakers

Rule 1: Make the smallest edit that breaks the code, then name what you edited

When two kinds of connascence both seem to fit, imagine the one tiny edit that breaks the other side:

  • You changed a literal ("timeout" → "timeoutSec", 75 → 100, "gold" → "Gold"): Value.
  • You changed the shape of the data (field renamed, string → number, new required field): Type.
  • You changed a step of a computation that someone else repeats (concatenation order, a formula, a separator built in code): Algorithm.
  • You swapped order (arguments, array slots, CSV columns): Position.

ConfigStore: the most likely break is a typo in "timeout". That's a literal, so the answer is Value. Tiers: three functions share the same string literals "bronze"/"silver"/"gold", and each function's rule is different, so nothing is computed the same way twice. That's why it's Value, not Algorithm. Algorithm needs the same computation derived independently (as in the PasswordHasher or InvoiceExporter labs).

Rule 2: A fallback default turns an explicit error back into a silent one

// What you wrote in LAB03.4
const handlingFees: Record<string, number> = { envelope: 1.5, box: 4.0, pallet: 22.0 };
const handling = handlingFees[shipment.packageType] ?? 0;

Add "crate" to the type and this still compiles, and crate shipments get handling = 0. That's exactly the silent bug the ticket asked you to prevent. Use the union as the key, with no fallback:

type PackageType = "envelope" | "box" | "pallet";
const HANDLING_FEE: Record<PackageType, number> = { envelope: 1.5, box: 4.0, pallet: 22.0 };
const handling = HANDLING_FEE[shipment.packageType];   // no ?? needed

Now adding "crate" to PackageType makes the HANDLING_FEE literal fail to compile ("Property 'crate' is missing"). The coupling went from implicit Value to explicit Type. One sentence like that is worth most of the marks in a "justify" box.

Same trap in the Tier lab. The if-chain's last line, return 0.1; // gold, is a catch-all, so a platinum account falls through and silently gets gold's values. It never throws. Whenever you see a catch-all return or else, the honest answer to "how do you find out?" is "silently wrong".

Cohesion tie-breakers

Rule 3: Data means the same source, not the same field

If both blocks read the same object or array, they share a Data binding, even when one walks it and the other only calls .length.

Rule 4: Logic means the same condition, so any if between the blocks breaks it

Ask: "Is there any run of this method where one block executes and the other doesn't?" If yes, the answer is Logic = false. A config flag, a weekday check, or a seatsLeft === 0 test all break it.

Rule 5: Order means one block writes something the other reads

Two blocks that only read the same field can be swapped safely. Order holds only when one block changes state that the other depends on. Also check whether the write actually affects what the other block looks at. In closeOutDay, (C) changed pending → cancelled, but (A) only counted paid and refunded, so Order was false.

Testability tie-breaker

Rule 6: Splitting a method into smaller ones raises both properties

Observability goes up because each intermediate result is returned. Controllability goes up because a test can feed each rule exactly the input it wants (shipping(100)) instead of reverse-engineering an item list that produces exactly 100 after discount. "Can I choose what this rule sees?" is a controllability question.

Practice: tie-breakers on fresh code

Commit before you click. 

function onSignup(user: User) {
  const welcome = template("welcome", user.name);   // (1)
  if (user.referrer) {
    credit(user.referrer, 10);                       // (2)
  }
  analytics.track("signup");                         // (3)
  mailer.send(user.email, welcome);                  // (4)
}

Which bindings do lines (2) and (3) share?

None. They share no data, and swapping them changes nothing. Logic fails because (2) only runs when there's a referrer (Rule 4). This is the exact trap from LAB02.12.

Which bindings do lines (1) and (4) share?

All three. (4) uses welcome, which (1) produced (Data). Both always run (Logic). You can't send the message before you build it (Order).

const active = users.filter(u => u.active).length; // (A) and then const emails = users.map(u => u.email); // (B), with no condition around either. Which bindings hold?

Data and Logic. They read the same source, even though they use different fields (Rule 3), and both always run. Neither writes anything, so you can swap them (Rule 5).

SettingsPage does localStorage.setItem("prefs", JSON.stringify(p)). ThemeLoader does JSON.parse(localStorage.getItem("prefs")!) as Prefs. What is the strongest connascence?

Value. The smallest edit that breaks it is a typo in the key "prefs" (Rule 1). It's the ConfigStore pattern again. Type is also present, but the cast doesn't check anything.

const LIMIT: Record<string, number> = { free: 5, pro: 50 }; return LIMIT[plan] ?? 5;, where plan: "free" | "pro". Someone adds "team" to the union. How do you find out?

Silently wrong. A string key accepts anything, and ?? 5 hands team accounts the free limit. This is Rule 2.

Same as the last question, but the table is typed Record<Plan, number> (where Plan = "free" | "pro") and there's no ??. Now someone adds "team" to Plan.

Compile error at the table: "team" is missing. The coupling is explicit now.

UserCache.put stores under "user:" + id. In another file, Profile.load reads cache.get("user:" + id). What is the strongest connascence?

Algorithm. Both files build the key the same way, which is the same shape as the building-id example in Lesson 1. Fix: export a userKey(id) function, so the coupling becomes Name.

A test for ClockGreeter reads new Date().getHours() itself and copies the method's if-chain to predict the expected string. What's the main flaw?

A test that re-derives the answer using the same algorithm is coupled to the code it tests. If the code is wrong, the test is wrong in the same way, and it passes. The real fix is to make the hour controllable, which test doubles (Lesson 3) do.

export class Parking {
  fee(minutes: number, vehicle: "car" | "motorbike" | "truck"): number {
    let rate = 0;
    if (vehicle === "car") rate = 3;
    if (vehicle === "motorbike") rate = 1.5;
    if (vehicle === "truck") rate = 6;
    const hours = Math.ceil(minutes / 60);
    return Math.min(hours * rate, 24);
  }
}
