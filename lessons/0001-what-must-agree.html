What must agree with what?

Naming the coupling behind an expensive change: connascence, degree, and locality

The win. Given code you have never seen, you can say which two pieces must agree, name the kind of agreement (its connascence), say whether the compiler would catch a mismatch, and explain how degree and locality make a change more expensive. Almost every midterm question about coupling starts with this step.

The one question

The course asks one question at every scale: what will the next change cost, and why? When you want to explain the cost of a change, start by asking which two places must stay in agreement. If one changes, the other has to change too. That relationship is coupling. The reader measures it three ways[1]:

AttributeQuestion to askMakes a change cost more because…
DegreeHow many connections?more places to visit, read, and edit
LocalityHow far apart are they?far-away places are harder to find, and easier to forget
Strength (connascence)What exactly must they agree on?stronger agreements are harder to keep in sync

Five kinds of agreement

The reader lists five types of connascence (from the Latin for "born together"). They're shown here in the order the reader gives them. Treat the later ones as stronger[1]:

Connascence of…Must agree onTiny example
Namewhat something is calledrename findUserById → every call site changes
Typethe shape of the dataadd a required field → every caller must supply it
Valuea specific literal"pending" hard-coded in validation, reports, and UI
Positionargument ordercreateInvoice(id, start, end, total, tax), where a caller swaps total and tax
Algorithma computation done the same wayone class encrypts, and another must decrypt with the same algorithm
Explicit or implicit? The most dangerous coupling is the kind the compiler can't see. If you rename a function, TypeScript flags every broken call, so that coupling is explicit. If you swap two number arguments, or forget one copy of "pending", everything still compiles, and the mistake fails silently at runtime. That coupling is implicit[1]. On the exam, saying whether a coupling is explicit or implicit is often what separates a full-marks answer from a partial one.

Most pairs of code agree on several things at once. In the reader's example below, inverseOperation depends on mysteriousOperation's name and its argument order. Name the strongest connascence, because it's the most significant one[1]:

function mysteriousOperation(x: number, y: number) { return x - y; }
function inverseOperation(x: number, y: number) { return mysteriousOperation(x, y); }
// Name + Position. Position is strongest, and it's implicit: both are numbers.

Here's how this connects to your project. D1 asked you to describe "what had to agree with what" when you added campus. That question asks you to find the connascence. Request 1 forced changes in parsing, PUT, search, tests, and openapi.yml: a high-degree, low-locality change. Request 2 was one method. The difference in effort between them is what this lesson helps you explain.

Practice: name it

Answer from memory, and commit before you click. Each question locks after your first answer.

Two files check if (order.status === 3), where 3 means "shipped". Product wants a new status inserted before "shipped", so "shipped" becomes 4. What is the connascence between the two files?

This is Value. Both files must agree on a specific literal. A magic number is the reader's special case of connascence of value. It's implicit: if you miss one file, it still compiles.

sendEmail(to: string, from: string, subject: string, body: string) is called from 14 places. Which kind of connascence makes a careless edit at one call site most dangerous?

This is Position. All four parameters are string, so swapping to and from compiles fine and sends mail the wrong way. It's the reader's createInvoice case. A degree of 14 means 14 chances to get it wrong.

Signup stores sha256(password + "s4lt"). In another module, Login recomputes sha256(password + "s4lt") and compares the two. What is the strongest connascence?

This is Algorithm. Both modules must do the computation the same way. (They also share the value "s4lt", but the strongest bond is the duplicated algorithm, and that's the one to name.) Changing the hash in one module silently locks every user out.

getCoords() returns { lat, lon }. A caller reads result.lat. The team changes the return value to { latitude, longitude }. What were the caller and callee agreeing on?

This is Type: the shape of the data. Field names are part of the shape here. With TypeScript types on the return value, this coupling is explicit. If the result is passed around as any, it becomes implicit.

The dataset parser builds each building's id as shortname + "_" + number. The PUT handler rebuilds the id the same way to find the building on disk. What is the connascence?

This is Algorithm. Two places compute something "the same way". If someone changes the separator to "-" in the parser only, PUT silently stops finding buildings. You can weaken it to Name by extracting a buildingId(shortname, number) function that both places call.

You replace the duplicated "pending" literals with a STATUS_PENDING constant that every module imports. Is the coupling between those modules now stronger or weaker?

The coupling is Weaker. Agreement on a value becomes agreement on a name, and the compiler checks names (explicit). The coupling isn't removed, though: the modules still depend on the constant. The goal is loose coupling, not zero coupling.

validateKey() is called in 20 places across 9 files, and its signature must change. Which attributes make this change expensive?

The answer is Degree and locality. There are 20 connections (degree), spread across 9 files (locality). This is the reader's own example: you visit, read, and edit each site[1].

Exam-style: justify it

This is the kind of question the midterm asks: read unfamiliar code, say what's wrong, and argue for a change. Write your answer before you look at the rubric.

QueryValidator.ts 
const VALID_KEYS = ["id", "name", "address", "lat", "lon"];
export function isValidKey(k: string): boolean { return VALID_KEYS.includes(k); }
QueryEngine.ts 
function getField(b: Building, k: string): string | number {
  switch (k) {
    case "id": return b.id;       case "name": return b.name;
    case "address": return b.address;
    case "lat": return b.lat;     case "lon": return b.lon;
  }
  throw new Error("unreachable");
}
openapi.yml 
key: { type: string, enum: [id, name, address, lat, lon] }

Q. A teammate adds a campus field to Building and updates QueryValidator.ts only. (a) What goes wrong, and when? (b) Characterize the coupling among these three files using the course's vocabulary. (c) Propose one change that weakens it, and state one cost of that change.
